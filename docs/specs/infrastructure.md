# Спецификация: инфраструктура и окружения

Статус: локальное окружение реализовано и проверено, продакшен описан планом. Дата: 2026-11-01.

## Локальное окружение (Docker)

Файл [compose.yaml](../../compose.yaml). Сейчас один сервис, состав будет расти:

| Сервис | Образ | Назначение | Статус |
|---|---|---|---|
| `db` | `postgres:17-alpine` | База данных (ADR-0003) | работает |
| CMS | зависит от решения в [ADR-0002](../adr/0002-headless-cms-directus.md) | Админка, каталог, заявки | ждёт решения |
| `web` | Nuxt (Node 24) | Витрина в контейнере, нужна для проверки продакшен-сборки | позже |

### Быстрый старт

```bash
pnpm env:init      # один раз: создаёт .env со случайным паролем базы
pnpm db:up         # запускает базу и ждёт, пока она станет здоровой
pnpm db:psql       # консоль psql
pnpm db:backup     # резервная копия в backups/ (формат pg_dump -Fc)
pnpm db:restore backups/<файл>.dump
pnpm db:down       # остановить, данные сохраняются
pnpm db:reset      # ОСТОРОЖНО: останавливает и удаляет все данные базы
```

Нужен Docker Desktop (на Windows с WSL2). После перезагрузки компьютера сначала запустите Docker Desktop.

### Что проверено на практике

| Проверка | Результат |
|---|---|
| Версия | PostgreSQL 17.11 |
| Кодировка и сортировка | UTF-8, провайдер ICU, локаль `ru-RU`: сортировка идёт по русскому алфавиту (Е, Ё, Ж), а не по кодам символов |
| Часовой пояс | `Europe/Minsk` |
| Данные при перезапуске контейнера | сохраняются (именованный том `pgdata`) |
| Резервная копия и восстановление | `pg_dump -Fc` и `pg_restore`: данные испортили, восстановили из копии, всё вернулось |
| Доступ | порт опубликован только на `127.0.0.1`, неверный пароль отклоняется |
| Секреты | пароль генерируется случайно, `.env` и `backups/` в git не попадают |

### Правила

- Пароль и другие секреты только в `.env` (локально) и в переменных окружения сервера. В git лежит только `.env.example`.
- Порт базы наружу не открываем ни локально (только `127.0.0.1`), ни на сервере.
- Схема данных меняется только миграциями, которые лежат в репозитории (способ зависит от выбранной CMS). Руками в базе схему не правим.
- Перед рискованной правкой делаем `pnpm db:backup`.
- Версию образа закрепляем. Обновление мажорной версии PostgreSQL делаем осознанно через дамп и восстановление.

## Продакшен (план, VPS на hoster.by, ADR-0005)

Не реализовано, это требования к будущей настройке.

- Docker и Docker Compose на VPS, отдельный файл `compose.prod.yaml`.
- Перед сервисами обратный прокси (Caddy или Nginx) с HTTPS (Let's Encrypt), сжатием, кэшем статики, редиректами (`http→https`, слеш на конце, `www`), заголовками безопасности. SEO-требования: [seo.md](seo.md).
- Наружу открыты только 80 и 443 (и SSH по ключу). База и CMS доступны только внутри сети Docker. Админка за прокси, по возможности с ограничением по IP или двухфакторной защитой.
- Секреты через переменные окружения сервера, не в образах.
- **Резервные копии**: ежедневный `pg_dump` по расписанию, хранение нескольких последних копий, **копия вне сервера** (иначе при потере VPS теряется всё), регулярная проверка восстановления.
- Мониторинг доступности и места на диске, ротация логов.
- Обновления: образы с закреплёнными версиями, обновление по расписанию с резервной копией перед ним.
- Размер VPS ориентировочно 2 vCPU и 4 ГБ памяти для Nuxt, CMS и PostgreSQL вместе. Уточнить по факту нагрузки и по выбранной CMS.
- Персональные данные клиентов лежат в этой базе: расположение сервера, доступ и копии учитываются в [legal-privacy.md](legal-privacy.md).

## Открытые вопросы

- Выбор CMS (см. ADR-0002), от него зависят сервисы и миграции.
- Тариф VPS на hoster.by: есть ли Docker, root и сколько ресурсов.
- Где хранить внешние копии базы (второй сервер, облачное хранилище, домашний компьютер).
- Нужен ли CI с настоящей базой для тестов приёма заявок (появится вместе с бэкендом заявок).
